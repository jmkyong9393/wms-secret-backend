## 🏛️ 1. 왜 FastAPI 단일 아키텍처인가? (단일 언어의 결합력)

메인 백엔드 담당자의 강점(FastAPI)과 AI 생태계와의 완벽한 결합을 위해 **FastAPI 단일 아키텍처**로 최종 결정했습니다. 에이전트별로 MSA 파드를 분리하는 방식은 배제하고, 오직 FE, BE, AI-Worker 단위로만 파드를 분리하여 효율을 높입니다.

### 1.1 FastAPI의 강력한 이점
1. **언어 장벽 제거:** 메인 API 서버와 AI 워커가 모두 Python 기반이므로, Pydantic 모델과 DB 스키마를 공유하여 개발 속도를 2배 이상 끌어올렸습니다.
2. **AI 네이티브 생태계:** LangGraph, LLM 호출 등 인공지능 관련 라이브러리들은 모두 Python에 최적화되어 있습니다. FastAPI는 이러한 비동기 AI 모듈들을 백그라운드에서 가장 매끄럽게 처리할 수 있는 웹 프레임워크입니다.
3. **K8s 기반 약점 방어:** 단일 언어 구조에서 발생할 수 있는 병목(단일 파드 부하)은 K8s의 HPA(오토스케일링)로 완벽히 방어합니다. AI 연산으로 인해 파드의 CPU가 70%를 넘어가면 즉각적으로 파드를 복제하여 트래픽을 분산시킵니다.

### 1.2 K8s HPA를 통한 오토스케일링
* 단일 FastAPI 환경에서도 K8s의 오케스트레이션은 필수적입니다. 물류 창고의 상하차 피크 타임(오전 9시~11시) 시 트래픽 부하가 발생할 때, HPA(Horizontal Pod Autoscaler)가 CPU와 메모리 사용량을 실시간 감지하여 Pod을 유연하게 스케일 아웃함으로써 인프라 효율성을 극대화합니다.

## 🤖 2. LangGraph Supervisor (Star Topology) 기반 다중 에이전트 상세 설계

과거의 단순 순차적(Sequential) 파이프라인에서 벗어나, 중앙의 **Supervisor Agent**가 각 전문 에이전트(Vision, Policy, Critic, Report)를 별형(Star Topology)으로 조율하고 유연하게 라우팅(Fast-track 등)합니다. 또한 **LLMOps 체계(LangSmith 트레이싱, Reason Codes, MemorySaver)**를 도입하여 추적과 예외 처리를 고도화했습니다.

### 🕵️ Agent 1: Vision Inspector (시각 검수자)
* **사용 모델:** `GPT-4o` (가장 시각 인지력이 뛰어난 모델)
* **역할:** 사내 규정이나 주관을 배제하고, 오직 사진에 존재하는 물리적 결함(팩트)만 추출합니다.
* **프롬프트 전략 (Relative Ratio BBox 연산):** "너는 정밀 검사관이야. 2D 사진 원근감의 한계로 인해 절대적 cm 측정은 불가능하므로, Bounding Box를 그려 **책 전체 면적 대비 얼룩 픽셀의 비율(%)**, 또는 **책 길이 대비 찢어진 길이의 비율(%)**을 계산해서 팩트 수치만 JSON으로 뱉어." 만약 결함이 없는 최상급(Mint) 상태라면, 즉시 **Fast-track (Auto-refund)** 라우팅을 타도록 Supervisor에게 신호를 보냅니다.

### ⚖️ Agent 2: Policy Decision (규정 판독자)
* **사용 모델:** `GPT-4o-mini` (텍스트 논리 분석에 특화, 저비용)
* **역할:** Agent 1이 찾은 팩트(상대 비율)와 'UBCI 중고 매입 환불 규정 DB(RAG)'를 맵핑하여 **UBCI(Used Book Condition Index)** 점수를 깎습니다.
* **프롬프트 전략 (Page-level Penalty):** "자체 개발 상태 평가지수(UBCI) 기준상 2cm(길이 비율 10%) 이상 찢어짐은 20점 감점이야. Vision Agent가 넘겨준 데이터를 바탕으로 감점하되, 억울한 폐급 처리를 막기 위해 **한 페이지에 여러 하자가 있어도 동일 유형은 1회만 감점(Page-level Penalty)** 처리해. 최종 UBCI 점수가 70점 미만이면 매입 반려로 판정해."

### 🧐 Agent 3: Critic (교차 검증자 / 환각 방어의 핵심)
* **사용 모델:** `GPT-4o-mini`
* **역할:** Agent 1과 Agent 2의 결과를 종합하여 논리적 모순이 없는지 비판적 시각(Self-Reflexion)으로 재검토합니다. 이때 **Reason Codes(명시적 에러 분류 코드)**를 활용하여 환각 여부를 체계적으로 분류합니다.
* **프롬프트 전략:** 
  1. "Vision Agent가 얼룩을 찾았는데 Policy Agent가 정상으로 승인했어. 규정집에 비추어 이 판정에 모순이 없는지 검토해."
  2. "사진의 화질이 너무 흐리거나 빛 반사가 심해서 애초에 Vision Agent의 결과 자체를 믿을 수 없다고 판단되면, **'판독 불가'**를 선언해." (이 경우 관리자 대시보드로 즉시 이관됨 - 투트랙 재시도 전략)

### 📝 Agent 4: CS Reporter (고객 응대 작성자)
* **사용 모델:** `GPT-4o-mini`
* **역할:** Critic 검증까지 최종 통과하여 '반품 거절(Rejected)'이 확정되었을 때, 거래처(또는 B2C 고객)에게 보낼 정중한 사유서를 작성합니다.
* **프롬프트 전략:** "앞서 확정된 결함 사유(예: 3cm 찢어짐)를 바탕으로, 당사의 반품 거절 정책에 의거하여 정중하고 프로페셔널한 거절 사유서를 작성해 줘."

## 🛠 3. 클라이언트 최적화 딥다이브 (Edge Computing)

### 3.1 HTML5 Canvas 기반 이미지 리사이징
* 요즘 스마트폰 카메라의 원본 용량은 5~10MB에 달합니다. 이를 그대로 K8s Backend Pod으로 전송하면, 수십 명의 작업자가 동시에 업로드할 때 서버 대역폭이 뻗어버리게 됩니다.
* **해결책:** 작업자의 스마트폰 브라우저(Frontend Pod이 제공하는 PWA 환경)에서 `HTML5 Canvas API`를 활용하여 촬영 즉시 백그라운드에서 이미지를 1080px 해상도의 `WebP` 포맷으로 압축합니다. 
* 용량이 500KB 이하로 1/10 수준으로 줄어들며, 백엔드를 거치지 않고 바로 AWS S3로 **다이렉트 업로드(Direct Upload / Presigned URL)**를 꽂아 서버 부하를 제로(0)로 만듭니다.

## ⚙️ 4. 대용량 비동기 통신 및 인프라 모니터링 (Backend DeepDive)

백엔드 팀원 3인의 전문성을 살린 트래픽 최적화 및 안정성 모니터링 특화 아키텍처입니다.

### 4.1 SSE(Server-Sent Events) 기반 비동기 푸시의 필요성
* 모바일 클라이언트에서 검수 요청을 보낸 후 15초 동안 응답을 기다리게(Polling) 만들면 브라우저 타임아웃이 발생하거나 불필요한 네트워크 부하가 생깁니다.
* **해결책:** **FastAPI의 `StreamingResponse`**를 활용하여 단방향 데이터 스트리밍(SSE) 채널을 엽니다. 클라이언트가 억지로 폴링하는 대신, FastAPI 서버가 클라이언트와 단일 연결을 유지한 채 검수 진행 상태(진행 중 -> Critic 검증 중 -> 완료)를 단방향으로 스트리밍해줌으로써 DB 커넥션 부하를 획기적으로 낮췄습니다.

### 4.2 LLMOps 및 인프라 모니터링 (LangSmith, Prometheus & Grafana)
* 4-Agent 체인은 내부 연산(OpenAI API 대기)이 많아 병목 구간(Bottleneck)을 추적하기 어렵고, 환각을 디버깅하기 힘듭니다.
* **해결책:** **LangSmith**를 연동하여 Multi-Agent의 트레이싱(Tracing)과 Reason Codes 발생 빈도를 시각화합니다. 또한 K8s 클러스터 내에 **Prometheus & Grafana**를 띄워 FastAPI의 응답 속도, OpenAI API 호출 지연 시간(Latency), 에이전트별 토큰 사용량, Pod의 CPU/RAM 사용량을 직관적으로 모니터링합니다.

## 1. 스마트폰 UX/UI 및 네트워크 음영 문제 대처 방안

스마트폰을 손에 들고 일일이 바코드를 찍고 사진을 찍는 행위는 작업 속도를 3배 이상 지연시킵니다. 이를 소프트웨어와 저렴한 하드웨어의 조합으로 타파해야 합니다.

### 💡 해결책 1-A: 'DIY 고정형 비전 검수대' 구축 (스마트폰 거치대 + 풋페달)
*   **접근법:** 스마트폰을 '모바일 기기'가 아닌 **'저렴한 고정식 웹캠'**처럼 취급합니다.
*   **구현 방법:** 
    1. 작업대에 3~5만 원대 **수직 거치대(Overhead Stand)**를 설치하여 스마트폰을 고정시킵니다. 작업자의 양손은 자유로워집니다.
    2. 스마트폰과 **블루투스 풋페달(Foot Pedal)** 또는 저렴한 무선 바코드 스캐너를 페어링합니다.
    3. 프론트엔드(Next.js)에서 '스페이스바'나 특정 키보드 입력(페달/스캐너 입력값)이 들어오면 즉시 HTML5 Canvas가 사진을 캡처하고 업로드하도록 이벤트를 바인딩합니다.
*   **기대 효과:** 수천만 원짜리 산업용 컨베이어 비전 없이도, 작업자가 책을 거치대 아래에 쓱 밀어 넣고 발로 페달을 밟기만 하면 검수가 끝나는 완벽한 UX를 창출할 수 있습니다. (시연 때 이 모습을 보여주면 심사위원들에게 엄청난 임팩트를 줍니다)

### 💡 해결책 1-B: PWA Offline-First 큐 (네트워크 단절 방어)
*   **접근법:** 와이파이가 끊겨도 작업자는 에러 창을 보지 않아야 합니다.
*   **구현 방법:** Next.js의 **Service Worker와 IndexedDB**를 활용합니다.
    1. 네트워크 음영 구역에서 페달을 밟아 촬영되면, 사진(WebP)과 책의 메타 데이터를 브라우저 내장 DB인 `IndexedDB`에 임시 저장(Enqueue)합니다.
    2. Service Worker가 백그라운드에서 네트워크 상태를 모니터링하다가 와이파이가 다시 연결되는 즉시, 쌓여있던 큐를 S3로 순차 동기화(Background Sync) 시킵니다.
*   **기대 효과:** 물류 창고의 열악한 통신 환경을 소프트웨어의 비동기 처리로 완벽히 은닉(Abstraction)할 수 있습니다.

## 2. FastAPI Background Tasks 데이터 유실 대처 방안

K8s 환경에서 메모리 기반의 Background Tasks는 '시한폭탄'입니다. 데이터 유실을 막기 위해 상태(State)를 안전한 곳에 기록하는 큐(Queue) 시스템이 반드시 필요합니다.

### 💡 해결책 2: PostgreSQL 기반 트랜잭션 큐 (Celery/Redis 배제)
별도의 무거운 큐 시스템(Celery/Redis 등)을 추가하지 않고, 현재 메인 DB로 사용할 **PostgreSQL**을 메시지 큐처럼 활용하는 것이 가장 안전하고 빠릅니다. (Supabase는 Plan B로 고려)
*   **구현 방법 (`Celery/Redis 비동기 폴링`):**
    1. API를 받는 **Web Pod**과 AI 추론을 담당하는 **Worker Pod**의 코드를 물리적/논리적으로 분리합니다.
    2. Web Pod은 API 요청이 오면 DB의 `return_jobs` 테이블에 `status='PENDING'`으로 Insert만 하고 즉시 `202 Accepted`를 반환합니다.
    3. 수많은 Worker Pod들은 1초마다 DB를 폴링하며 다음 쿼리를 실행합니다.
       `SELECT * FROM return_jobs WHERE status = 'PENDING' Celery/Redis 비동기 폴링 LIMIT 1;`
    4. 이 쿼리는 데이터베이스 락(Lock)이 걸린 행을 건너뛰므로, Worker 10대가 동시에 조회해도 중복 작업이 발생하지 않습니다.
    5. Worker가 중간에 죽더라도, 일정 시간(예: 5분) 업데이트가 없는 작업을 다시 `PENDING`으로 돌리는 스케줄러만 있으면 무한히 재시도되어 유실이 없습니다.
*   **기대 효과:** 아키텍처 복잡도 증가 없이, K8s HPA가 아무리 Pod을 죽이고 살려도 AI 판독 데이터가 영구적으로 보존됩니다.

**평가 대상:** 피드백이 반영된 최신 기획서 및 아키텍처 문서
**최종 등급:** **S (Outstanding)**

## 1. 각 분야별 세부 등급 및 평가 사유

### 📈 비즈니스 타당성 및 시장성 (Business Viability)
*   **등급:** **S**
*   **평가 사유:** 도서 물류라는 명확한 페인포인트를 타겟팅하여 1건당 30원 미만의 비용으로 검수 시간을 1/4(120초 ➡️ 30초)로 단축한다는 ROI가 확실합니다. **특히 UBCI 중고 매입 기준을 '상대 비율(Relative Ratio BBox)'과 '페이지 단위 감점(Page-level Penalty)'이라는 정밀한 수학적 모델(UBCI)로 치환해 낸 점은 비즈니스 로직과 AI 기술이 완벽히 결합된 사례입니다.**
*   **피드백 반영의 백미:** 이전 기획의 최대 약점이었던 '스마트폰 수작업 촬영'을 **'거치대 + 풋페달' 기반의 DIY 고정형 비전 스캐너로 피벗(Pivot)**한 점이 결정적입니다. 현장의 작업 피로도를 낮추면서도 '도입 비용 0원'이라는 B2B SaaS의 세일즈 포인트를 완벽하게 지켜냈습니다.

### 🏗️ 기술 아키텍처 및 안정성 (Technical Architecture)
*   **등급:** **S+**
*   **평가 사유:** 7인 주니어 프로젝트라고는 믿기 힘든 **엔터프라이즈급 방어적 아키텍처(Defensive Architecture)**를 완성했습니다.

## 1. 비즈니스 모델의 치명적 한계 (Business & Market Limits)

*   **창고 현장의 현실(UX/UI) 무시:** 작업자가 스마트폰으로 사진을 찍는 것을 '도입 비용 0원'이라는 장점으로 포장했으나, 실제 물류 현장에서 장갑을 낀 채 스마트폰 앱을 켜고 초점을 맞춰 사진을 찍는 행위는 전용 바코드 스캐너나 거치형 카메라보다 **작업 피로도와 소요 시간을 훨씬 증가**시킵니다. 와이파이 음영 구역이 많은 물류 창고 특성을 고려하면 통신 지연 문제도 심각합니다.

---

## 2. 아키텍처 설계의 기술적 결함 (Architecture Flaws)

*   **FastAPI Background Tasks의 치명적 약점 (데이터 유실):** 비동기 처리를 위해 FastAPI의 `Background Tasks`를 사용한다고 기획되었으나, 이는 **메모리 상에서만 동작**합니다. 만약 검수가 진행되는 도중 HPA에 의해 해당 Pod이 스케일 인(Scale-In)되거나 서버 에러로 재시작된다면, 진행 중이던 AI 작업 로그와 재고 상태는 **영구적으로 증발(Lost)**합니다. 이를 방지하기 위해 PostgreSQL의 `Celery/Redis 비동기 폴링` 기반 트랜잭션 큐 도입이 필수적입니다.
*   **Supabase 롤백 비용이 '0'이라는 환상:** AWS RDS/S3 세팅 병목 시 Supabase로 롤백하겠다는 플랜은 좋으나, "코드 수정 비용이 0에 수렴한다"는 것은 완벽한 오판입니다. AWS Boto3를 이용한 S3 Presigned URL 발급 로직과 Supabase Storage의 API 규격은 완전히 다릅니다. ORM(SQLModel)을 쓴다 해도, 인프라 전환 시 코드 레벨의 수정과 의존성 변경은 필연적입니다.
*   **엣지 리사이징(HTML5 Canvas)의 OOM 리스크:** 저사양 스마트폰을 사용하는 창고 작업자 기기에서 10MB 이상의 사진을 연속으로 Canvas에 올려 리사이징(WebP 변환)할 경우, 브라우저의 메모리 누수(Memory Leak) 및 OOM(Out of Memory) 크래시가 발생할 확률이 매우 높습니다.

---

## 3. 개발 일정 및 프로젝트 관리의 허상 (Unrealistic Management)

*   **K8s(EKS) 오버엔지니어링의 늪:** 6+1주(6주 코어 개발)라는 기간 내에 주니어 혹은 학생 레벨의 인원 7명이 LangGraph 파이프라인(UBCI 비율 연산 포함) 연동, WMS 코어 로직 구현, 프론트엔드 최적화까지 완수하면서 **AWS EKS 기반의 MSA까지 배포한다는 것은 사실상 불가능**에 가깝습니다. 비록 Tech PM이 Git Gatekeeper와 인프라 전담으로 빠졌다고 하더라도, 트래픽 오토스케일링이 진정 필요하다면 K8s가 아닌 AWS App Runner나 ECS 기반의 Serverless 컨테이너 환경으로 인프라 복잡도를 대폭 낮춰야만 코드 프리즈 데드라인을 맞출 수 있습니다.
*   **순차적 Multi-Agent의 병목 극복 과제:** 초기의 4개 에이전트(Vision -> Policy -> Critic -> Report)가 순차적으로 호출되는 구조는 최소 15초 이상의 지연을 유발합니다. 이를 Supervisor 중심의 Star Topology로 전환하여 정상품(MINT)은 Policy/Critic을 거치지 않는 **Fast-track(Auto-refund)** 처리로 병목을 극복해야 합니다.
