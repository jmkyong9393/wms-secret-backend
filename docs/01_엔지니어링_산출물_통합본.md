# 📋 [문서 1] 요구사항 정의서 (Requirements Definition)

- **최초 작성자 (PM):** 장문경
- **프로젝트명:** 멀티 에이전트 B2B 도서 반품검수 SaaS

## 1. 개요
도서 반품 시 발생하는 수작업 검수를 AI 에이전트를 통해 100% 자동화하여 인건비 병목을 해소하고 악성 환불 분쟁을 방지한다. 나아가 지능형 스마트 출고(Outbound) 파이프라인을 구축하여 주문, 포장, 판매에 이르는 창고 관리 프로세스를 혁신한다.

## 2. 과제 선정 배경 및 타당성 (References)
- **[배경 1] 신뢰성 하락 방어:** 반품 상품을 단순히 재판매하는 과정에서 검수 누락으로 소비자 불신이 발생한 사례(국민일보, "반품 상품 최상급 판매 논란")가 존재한다. 이에 객관적인 UBCI 점수와 디지털 품질 보증서 도입이 필수적이다.
- **[배경 2] 판매자 역량 및 자원 누수:** 빠른 검수 역량 부족으로 멀쩡한 도서가 폐기되는 물류 비용 누수(물류신문)를 막기 위해, 구조화된 결과를 30초 내에 내놓는 비전 AI의 도입이 시급하다.
- **[배경 3] 기술적 시의성:** 최근 비전 AI 검수 논문(arXiv:2502.09057)에서 제안된 '소수의 정상/불량 예시와 검수 기준 설명(Rule)'을 결합한 방법론은, 당사가 설계한 **Vision + Policy Agent 구조**의 기술적 우수성과 상용화 가능성을 완벽히 뒷받침한다.
- **[배경 4] Human-in-the-Loop:** AI가 100% 정확하지 않아도 모호한 건만 인간이 개입하는 체계(의류 불량 검수 사례 등)만으로도 도입 시 인원/시간 감축 효과(동아일보)가 확실하게 증명된다.

## 3. 기능적 요구사항 (Functional Requirements)
- **[FR-01]** 현장 작업자는 스마트폰 모바일 웹앱(PWA)을 통해 도서를 가이드라인에 맞춰 촬영할 수 있어야 한다.
- **[FR-02]** 모바일 클라이언트는 네트워크 부하를 줄이기 위해 HTML5 Canvas를 이용해 엣지단(스마트폰)에서 이미지를 리사이징/압축해야 한다.
- **[FR-03]** AI 에이전트는 [Vision, Policy, Critic, Report] 4단계로 역할을 분담하여 교차 검증을 수행해야 한다.
- **[FR-04]** 에이전트 판정이 실패하거나 모호함(Threshold 미달)으로 떨어진 경우, 관리자가 수동으로 승인/반려할 수 있는 대시보드를 제공해야 한다.
- **[FR-05]** 반려 판정 시, 거래처(고객사)에 송부할 '거절 사유서(Report)'가 자동 생성되어야 한다.
- **[FR-06]** 중고 매입 모드 촬영 시, AI는 자체 개발 상태 평가지수(UBCI) - 알라딘 참고에 의거하여 **상대 비율(Relative Ratio BBox) 연산**과 **페이지 단위 1회 감점(Page-level Penalty) 로직**을 적용해 최종 UBCI 점수를 산출해야 한다.
- **[FR-07]** (출고) 판매 시, 해당 도서의 UBCI 점수에 비례하여 동적 가격 할인(Dynamic Pricing)이 적용되어야 한다.
- **[FR-08]** (출고) 출고 속도를 분석하여 재고 고갈이 예상될 경우 출판사로 자동 발주(Demand Forecasting & Auto-PO)를 생성해야 한다.
- **[FR-09]** (출고) 재고 피킹 시, 오래된 재고 혹은 특정 UBCI 점수 기준으로 선입선출(FIFO by UBCI) 할 수 있도록 작업자에게 최적의 로케이션을 안내해야 한다.
- **[FR-10]** (출고) 주문된 도서들의 체적 데이터를 바탕으로 최적의 택배 박스 사이즈를 추천하는 3D Bin Packing (Box Optimization) 기능이 제공되어야 한다.
- **[FR-11]** (출고) 판매된 도서에 대해 Report Agent의 검수 결과가 포함된 디지털 UBCI 품질 보증서(QR/Link)를 구매자에게 발행할 수 있어야 한다.

## 3. 비기능적 요구사항 (Non-Functional Requirements)
- **[NFR-01]** 검수 1건당 사진 업로드 시점부터 최종 판정까지 **30초 이내**에 완료되어야 한다.
- **[NFR-02]** 피크 타임 트래픽 방어를 위해 K8s 기반 HPA(CPU 70% 임계치) 오토스케일링이 정상적으로 작동해야 한다.
- **[NFR-03]** 클라이언트(모바일)와 서버 간 상태 업데이트는 SSE(Server-Sent Events)를 통해 실시간 푸시되어야 하며, 폴링(Polling)으로 인한 서버 부하를 제거해야 한다.
- **[NFR-04]** 텍스트 전용 에이전트 3개는 GPT-4o-mini를 적용하여 건당 추론 비용을 30원 미만으로 억제해야 한다.

# 🏛️ [문서 2] 아키텍처 정의서 (Architecture Definition)

- **최초 작성자 (PM):** 장문경

## 1. 아키텍처 개요 (FastAPI Single Backend)
본 시스템은 개발 생산성과 AI 모델 연산 생태계 최적화를 위해 메인 서버와 AI 워커를 모두 **Python(FastAPI)** 기반으로 통일한 단일 백엔드 아키텍처로 설계되었습니다. 트래픽 안정성은 K8s 인프라를 통해 보완하며, UBCI 기반 동적 프라이싱, 수요 예측, 3D Bin Packing 로직이 통합되어 있습니다.

## 2. 계층별 기술 스택
- **Client Layer (FE):** Next.js 16 (App Router), React, HTML5 Canvas API (WebRTC/WASM 등 4대 극한 최적화 기술이 적용된 고성능 PWA 특화)
- **Core API & AI Layer (BE-2, AI, BE-1):** Python FastAPI, LangGraph, LLM(GPT-4o, GPT-4o-mini), SSE(StreamingResponse), 3D Bin Packing & 수요 예측 엔진
- **Data & Storage Layer:** PostgreSQL (Celery/Redis 비동기 폴링 큐 지원), Supabase(Plan B), Object Storage (S3 호환)
- **Infra / DevOps (Tech PM 장문경 전담 - Git Gatekeeper, K8s/EKS 인프라 매니저, Kanban 마스터, 통합 관리자 (Integration Manager), 트러블슈터 (Cross-functional Troubleshooter), 코드 검수 (Code Reviewer), 백엔드 API 개발/오케스트레이션 제외):** AWS EKS (또는 K3s), Docker, GitHub Actions, Prometheus, Grafana

## 3. 시스템 간 통신 규약
- **[Client <-> Core API]**: HTTP/HTTPS 기반의 표준 REST API 및 단방향 SSE(Server-Sent Events)를 통한 실시간 상태 푸시.
- **[Core API <-> AI Worker]**: FastAPI 애플리케이션 내부의 `비동기 데몬(Worker)`를 통한 비동기 위임 처리, 혹은 K8s 내부망을 통한 독립적 워커 파드 비동기 호출.

# 🗄️ [문서 3] ERD 설계서 (Entity Relationship Diagram)

관계형 데이터베이스(PostgreSQL)를 메인으로 사용하여 트랜잭션 무결성을 보장하되, LangGraph 기반 Multi-Agent 시스템이 뱉어내는 가변적이고 복잡한 상태(State) 기록은 `JSONB` 타입으로 묶어 유연하게 로깅합니다.

# [Sprint 1] 백엔드 코어 세팅 및 WMS DB 스키마 상세 기획안

본 기획안은 프론트엔드 팀이 병목 없이 개발을 시작할 수 있도록, **FastAPI 기반 백엔드 뼈대**를 구축하고 **WMS 코어 관계형 데이터베이스 스키마**를 상세하게 정의합니다.

## 1. Python 패키지 매니저 비교 및 추천

백엔드 개발 시 어떤 도구로 라이브러리(패키지)를 설치하고 관리할지 결정해야 합니다. 총 7명으로 구성된 팀의 6+1주라는 짧은 기한과 러닝 커브를 고려해 다음 세 가지를 비교했습니다.

| 툴 이름 | 특징 | 장점 | 단점 | 추천 여부 |
| :--- | :--- | :--- | :--- | :--- |
| **`pip` (기본)** | Python의 가장 기본적인 설치 도구 (`requirements.txt` 사용) | 배우기 쉽고 추가 설치가 필요 없음. 가장 익숙함. | 패키지 의존성이 꼬일 경우 해결이 어렵고, 설치 속도가 느림. | ⭐️⭐️ (보통) |
| **`Poetry`** | 현재 Python 생태계에서 가장 대중적인 모던 패키지 매니저 | 의존성 충돌을 완벽하게 계산해서 막아줌. `pyproject.toml`로 관리하여 깔끔함. | 락(Lock) 파일 생성 시 가끔 속도가 매우 느림. | ⭐️⭐️⭐️⭐️ (우수) |
| **`uv` (최신 트렌드)** | Rust 언어로 만들어진 초고속 패키지 매니저 | 기존 `pip`나 `Poetry` 대비 **10~100배 빠른 속도**. 문법이 `pip`와 거의 동일해 러닝 커브가 낮음. | 비교적 최신 툴이라 레퍼런스가 약간 적음. | ⭐️⭐️⭐️⭐️⭐️ **(최종 채택)** |

> [!TIP]
> **💡 최종 채택: `uv`** 
> 6+1주라는 짧은 기간 동안 총 7명의 팀원이 로컬에서 패키지를 설치하고 도커 이미지를 빌드하는 과정을 수십 번 반복해야 합니다. `uv`는 빌드 시간을 비약적으로 단축시켜 주며, 기존 `pip` 명령어와 거의 똑같이 쓸 수 있어 팀원들이 새로 공부할 필요도 없습니다.

## 3. WMS 코어 상세 데이터베이스 스키마 (SQLModel)

단일 책임 원칙에 따라 BE-3 박민우 님이 전담할 핵심 트랜잭션 테이블들입니다. 모든 테이블은 추후 분석을 위해 `created_at`, `updated_at`을 포함합니다.

### 1) `books` (도서 마스터)
* `id`: UUID (PK)
* `title`: String (도서명)
* `isbn`: String (바코드)
* `virtual_stock`: Integer (시연용 가용 총 재고)

### 2) `locations` (창고 진열대)
* `id`: UUID (PK)
* `zone`: String (예: A동)
* `rack`: String (예: 1열)
* `shelf`: String (예: 3단)
* `barcode`: String (로케이션 바코드 매핑용)

### 3) `inventory` (실제 재고 매핑)
* `id`: UUID (PK)
* `book_id`: UUID (FK -> books.id)
* `location_id`: UUID (FK -> locations.id)
* `quantity`: Integer (해당 위치에 있는 수량)

### 4) `orders` (출고/발주 트리거)
* `id`: UUID (PK)
* `customer_name`: String (B2B 고객사명)
* `type`: String (B2B_ORDER, AUTO_PO 등 - 수요 예측용 발주 포함)
* `total_price`: Integer (UBCI 기반 동적 가격 할인 적용됨)
* `status`: String (PENDING, PICKING, SHIPPED, RETURN_REQUESTED)

### 5) `return_jobs` (반품 작업 및 에이전트 로그 - 핵심 테이블)
* `id`: UUID (PK)
* `order_id`: UUID (FK -> orders.id)
* `book_id`: UUID (FK -> books.id)
* `status`: String (PENDING, PROCESSING, APPROVED, REJECTED)
* `image_urls`: JSONB (S3에 업로드된 반품/중고 사진 경로 배열)
* `ubci_score`: Integer (중고 매입 모드 시 산출된 감점 결과 점수)
* **`agent_logs`**: **JSONB** (Vision, Policy, Critic 에이전트가 주고받은 중간 State 데이터 전부 저장)
* `final_report`: Text (Report 에이전트가 쓴 사유서)

### 6) `inventory_logs` (재고 변동 트랜잭션)
* `id`: UUID (PK)
* `transaction_type`: String (INBOUND, OUTBOUND, RETURN, DISCARD)
* `book_id`: UUID (FK)
* `quantity_change`: Integer (+1, -1 등)

### 7) `outbound_logs` (출고 이력 및 품질 보증)
* `id`: UUID (PK)
* `order_id`: UUID (FK -> orders.id)
* `book_id`: UUID (FK -> books.id)
* `picked_location`: String (FIFO by UBCI에 의해 피킹된 로케이션)

### 8) `box_standards` (택배 박스 규격)
* `id`: UUID (PK)
* `name`: String (박스 규격명)
* `width`: Integer
* `length`: Integer
* `height`: Integer
* `max_weight`: Integer

# 🌊 [문서 5] 서비스 플로우 (Service Flow)

- **최초 작성자 (PM):** 장문경

## 1. End-to-End 사용자 및 시스템 여정 (User & System Journey)

1. **[작업자]** 스마트폰으로 모바일 웹앱(PWA)에 접속하여 입고된 반품 도서 또는 매입할 중고 도서의 바코드를 스캔하거나 도서명을 선택한다.
2. **[모바일 엣지]** 화면에 뜬 가이드라인 오버레이 박스에 맞춰 도서의 전면/측면/속지(중고 모드 시 다중 촬영)를 촬영한다. 브라우저 내부의 Canvas API가 10MB 원본 이미지를 500KB 이하로 즉시 압축한다.
3. **[모바일 클라이언트]** 압축된 이미지들을 Supabase Object Storage로 다이렉트 업로드(Direct Upload)하여 백엔드 서버의 트래픽을 아낀다.
4. **[Core API (FastAPI)]** 클라이언트는 업로드 완료된 `image_urls`와 `mode`를 담아 Core API로 검수 요청을 보낸다. 서버는 즉시 DB에 'PROCESSING' 상태를 기록하고 클라이언트와 SSE 연결을 맺는다.
5. **[Background Worker]** API 프로세스는 클라이언트 응답을 블로킹하지 않고, 내부 `비동기 데몬(Worker)`에 LangGraph Supervisor (Star Topology) 파이프라인 가동 지시를 위임한다.
6. **[AI Worker]** Supervisor 에이전트가 4개의 워커(Vision, Policy, Critic, Report)를 중앙 통제하며 동적 라우팅을 수행한다. 특히 Vision Agent 결과가 결함이 없는 정상품(MINT)일 경우 Policy 연산을 과감히 생략하는 **비용 최적화(Fast-track) 라우팅**이 적용된다. 결함 발견 시 자체 개발 상태 평가지수(UBCI) - 당사 자체 개발 기준에 따라 상대 비율 BBox 연산과 페이지 단위 감점을 통해 UBCI(Used Book Condition Index) 점수를 산출한다.
7. **[DB Update]** 최종 결론이 나면 워커 스레드가 결과를 DB(JSONB)에 최종 저장한다. (에이전트 실행 및 추적 로그는 LangSmith 연동)
8. **[Core API -> Client]** DB 업데이트 이벤트가 트리거되어 열려있던 SSE 통로를 통해 작업자의 스마트폰으로 "검수 완료(승인/반려)" 알림이 실시간으로 푸시된다.
9. **[Human-In-The-Loop (대시보드)]** Supervisor가 결정을 내리지 못한 모호한 케이스는 관리자 PC 대시보드에 알림이 가며, LangGraph의 `MemorySaver`를 통해 프로세스가 일시 정지(Pause)된다. 관리자가 수동 보정 후 승인(Approve)을 누르면 그 지점부터 그래프가 재개(Resume)되어 종료된다.

## 2. 출고 및 판매 여정 (Outbound & Sales Journey)

1. **[주문 접수 및 동적 프라이싱]** 고객이 시스템을 통해 도서를 주문하면, 해당 도서의 UBCI 점수에 비례하여 가격이 할인되는 Dynamic Pricing이 적용된다.
2. **[수요 예측 및 Auto-PO]** 출고 속도를 분석하여 특정 도서의 재고 고갈이 예상되는 경우, 출판사 시스템으로 예측 발주(Auto-PO)가 자동으로 전송된다.
3. **[작업자 피킹 할당]** 작업자에게 주문이 할당되며, FIFO by UBCI 원칙에 따라 가장 오래되었거나 조건에 맞는 재고의 로케이션(진열대)이 우선 안내된다.
4. **[3D Bin Packing]** 주문된 도서들의 체적을 계산하여 최적의 택배 박스 사이즈를 작업자에게 추천한다.
5. **[품질 보증서 발행]** 출고가 완료되면 해당 도서의 Report Agent 검수 결과가 담긴 디지털 UBCI 품질 보증서(QR/Link)가 생성되어 구매자에게 제공된다.

# 🎨 [문서 6] UI/UX 설계서 (UI/UX Design Concept)

- **최초 작성자 (PM):** 장문경

## 1. 현장 작업자용 Mobile PWA 뷰
- **디자인 컨셉:** 직관적이고 큼직한 '플랫 컴포넌트(Flat Component)' 디자인. 장갑을 낀 물류센터 작업자도 오터치 없이 한 손으로 조작 가능해야 함.
- **핵심 UX 요소:**
  - **카메라 오버레이:** 카메라 뷰파인더 위에 "책 모서리를 이 네모 안에 맞추세요"라는 가이드라인 실선 박스 제공.
  - **논블로킹 로딩:** 사진 업로드 후 "검수 중입니다..."라는 스피너(Lottie 애니메이션)가 도는 동안에도 다른 책의 바코드를 스캔할 수 있도록 비동기 UX 설계.
  - **명확한 피드백:** 검수가 끝났을 때 화면 전체가 초록색(✅ 승인) 또는 빨간색(❌ 반려)으로 번쩍이며 피드백 제공 (중고 매입 모드의 경우 산출된 UBCI 점수와 매입 등급 S/A/B/C를 함께 노출).

## 2. PC 관리자용 Dashboard 뷰 (WMS 통합 스타일)
- **디자인 컨셉:** 한눈에 다수의 처리 건을 통제하고 모니터링할 수 있는 다크모드/라이트모드 지원 데이터 시각화 보드.
- **핵심 UX 요소:**
  - **최상단 KPI 패널:** 금일 누적 처리량, 실시간 자동 승인율, 에이전트 반려율 등을 도넛 차트로 표기.
  - **Human Review Queue (수동 승인 대기열):** AI가 "확신도(Confidence) 80% 미만"으로 판단하여 사람의 결정을 요청한 리스트가 최우선으로 노출됨.
  - **Agent Log Visualizer (설명 가능한 AI UX):** 
    - 특정 검수 건을 클릭하면 모달 창이 뜬다.
    - 좌측에는 원본 사진(결함 부위에 Bounding Box 표시), 우측에는 4개의 에이전트가 어떤 대화를 나누고 결론을 내렸는지 카카오톡 대화방처럼 스크롤할 수 있는 디버깅 뷰 제공.
